## Требования
- [.NET 9.0+ SDK](https://dotnet.microsoft.com/download)
- Любой удобный редактор кода (Visual Studio, VS Code, Rider и т.д.)

В проекте используется подклчение к базе данных Postgres,
который необходимо поднять в Docker.

Файл docker-compose расположен в корне проекта.

---

## Запуск проекта

1. **Перейдите в директорию проекта**:
   
   cd <имя_папки_проекта>   

2. **Запустите контейнер с базой данных Postgres**
   docker compose up 

3. **Восстановите зависимости**:
   dotnet restore

4. **Соберите проект**:
   dotnet build

5. **Запустите проект**:
   dotnet run

6. **Откройте Swagger UI** в браузере:
   http://localhost:5105/swagger/index.html

## Конфигурация
- Порт по умолчанию: `5105` (можно изменить в `Program.cs` или `launchSettings.json`).
- Swagger автоматически настраивается при запуске.

### Описание

Схема базы данных будет создана автоматически во время запуска приложения.

Проект структурирован по четырем компонентам.

**Application** - содержит логику работы с бизнес-сущностями для решения определённых задач.
Здесь находятся интерфейсы репозиториев и сервисов, а так же DTO модели.

**Infrastructure** - в этом слое определяется работа с инфраструктурой — сервером СУБД, кешированием, внешними зависимостями.
Именно здесь определяются репозитории. Содержит реализацию интерфейсов, объявленых в Application.

В проекте используются миграции Code-First при помощи EntityFramework,
расположенные в в папке ../Infrastructure/Persistence/Migrations/.

Для выполнения миграций необходимо выполнять команды, находясь в ../Infrastructure/.

**Domain** Тут определены классы бизнес-сущностей и правила бизнес-логики.

**Presentation** Здесь объявлены контроллеры или minimal-api эндпоинты,
предоставляющие API для фронтенда, view-модели для представления данных и тому подобное.

Строка подключения находится в файле appsettings.json DefaultConnection.

### Бронирование события
Метод `BookEventAsync`создаёт бронирование на событие.

**Параметры:**
 | Параметр | Тип   | Описание                     |
 |-----------|-------|------------------------------|
 | `id`      | Guid  | Идентификатор события       |

возвращает **Booking** - модель бронирования.
   Поле          | Тип          | Описание                                      |
 |---------------|--------------|-----------------------------------------------|
 | Id            | Guid         | Уникальный идентификатор                      |
 | EventId       | Guid         | Идентификатор события                         |
 | Status        | BookingStatus| Статус бронирования                           |
 | CreatedAt     | DateTime     | Дата создания бронирования                    |
 | ProcessedAt   | DateTime?    | Дата обработки бронирования                   |


### BookingStatus
Статусы бронирования:
- `Pending` (1): Ожидает обработки.
- `Confirmed` (2): Подтверждено.
- `Rejected` (3): Отклонено.

Бронирование может принять статус Rejected = 3, если в результате фоновой обработки бронирований возникли ошибки.

В логику метода добавлена примитивная логика с блокировкой, которая 
предотвращает ситуации овербукинга. Это может произойти когда на текущем событии закончиваются
места, а количетсво броней приходит в большом количестве. Секция с блокировкой запрещает
изменять переменную AvailableSeats для события разу из нескольких потоков.

После успешного выполнения запроса придет ответ со статусом 202 Accepted.
Если у события количетсво доступных мест AvailableSeats на момент вызова метода BookEvent
будет равно 0 - метод вернет ответ в статусе StatusCodes.Status409Conflict 
с телом ответа, содержащего следующую ошибку:

```json
{
  "message": "No available seats for this event",
  "errors": []
}
```

После чего бронирование обработается в `BookingWorker`.

## Фоновая обработка

Фоновый сервис `BookingWorker` отвечает за обработку бронирований со статусом `Pending`.

Сервис обрабатывает входящие бронирования параллельно, используя SemaphoreSlim,
что позволяет быстро обрабатывать бронирования за счёт параллельной работы потоков.

Сервис работает непрерывно в фоновом режиме и выполняет следующие действия:

### Логика работы:
1. **Проверка новых бронирований:**
   - Каждые несколько секунд сервис проверяет наличие новых бронирований со статусом `Pending`.

2. **Обработка бронирования:**
   - Если найдены бронирования в статусе `Pending` - устанавливает статус бронирования на `Confirmed`.
   - Записывает текущую дату и время в поле `ProcessedAt`.
   - Может возникнуть ситуация, что событие было удалено во время обработки брони - в данном случае бронь получит статус Rejected = 3.

3. **Сохранение изменений:**
   - Обновляет информацию о бронировании в хранилище данных.
   - Логирует успешное завершение обработки.

### Проверка статуса бронирования

Возвращает текущее состояние бронирования.
