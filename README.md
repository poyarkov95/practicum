## Требования
- [.NET 9.0+ SDK](https://dotnet.microsoft.com/download)
- Любой удобный редактор кода (Visual Studio, VS Code, Rider и т.д.)

В проекте используется подклчение к базе данных Postgres,
который необходимо поднять в Docker.

Файл docker-compose расположен в корне проекта.

Решение было изменено на микросервисную архитектуру.
Теперь оно состоит из трех сервисов.

**UsersApplication**:
Сервис, который отвечает за вторизацию пользователя.
Генерирует токен, который необходим для работы с остальными сервисами.

**EventsApplication**:
Сервис, отвечающий за создание и администрирование событий.

**BookingsApplication**:
Сервис, отвечающий за создание и отмену бронирований на событие.

Доменные события и общие классы вынесены в отдельный проект Common.

## Система наблюдаемости

Для сервисов добавлен мониторинг.
Библиотека OpenTelemetry - инструмент для сбора метрик.

Каждый из сервисов экспортирует метрики по адресу: 
http://service-address/metrics,

которые потом собирает система мониторинга Prometheus.
На основе полученных данных можно строить графики для мониторинга системы.

В корне проекта добавлен файл dashboard.json, в котором
сконфигурирован дэшборд для Grafana. 
Это специализированная платформа для визуализации, анализа и мониторинга метрик.

Данный файл можно импортнуть в Grafana для отслеживания состояния системы.

Доступные метрики в дашборде:
Duration seconds - продолжительность запроса.
Active requests - текущее количество запросов в обработке.
Duration seconds bucket - Throughput (RPS).

Трейс запросов экспортируется в Jaeger, интерфейс которого доступен по адресу http://localhost:16686.
Jaeger позволяет остлеживать весь путь выполнения запроса, начиная от поступления запроса на сервис,
заканчивая выполнением запроса к базе данных.

Все эти три компонента добавлены в docker-compose.yml файл в корне проекта.
Для их работы необходимо запустить контейнеры prometheus, jagger, grafana.

## Запуск проекта

1. **Перейдите в директорию проекта**:
   
   cd <имя_папки_проекта>   

2. **Запустите контейнер с базой данных Postgres**
   docker compose up 

Следующие пункты необходимо проделать для каждого из трех сервисов.
  cd src/BookingsApplication 
  cd src/EventsApplication
  cd src/UsersApplication 

3. **Восстановите зависимости**:
   dotnet restore

4. **Соберите проект**:
   dotnet build

5. **Запустите проект**:
   dotnet run

6. **Откройте Swagger UI** в браузере:
   В консоли будет выведен адрес, на котором поднялся
   сваггер.
   Перейдите по необходимому адресу, который выведется в консоль.
   http://localhost:5197/swagger/index.html - BookingsApplication
   http://localhost:5166/swagger/index.html - EventsApplication
   http://localhost:5136/swagger/index.html - UsersApplication

### Описание

Каждый из микросервисов структурирован по четырем компонентам.

**Application** - содержит логику работы с бизнес-сущностями для решения определённых задач.
Здесь находятся интерфейсы репозиториев и сервисов, а так же DTO модели.

**Infrastructure** - в этом слое определяется работа с инфраструктурой — сервером СУБД, кешированием, внешними зависимостями.
Именно здесь определяются репозитории. Содержит реализацию интерфейсов, объявленых в Application.

В проекте используются миграции Code-First при помощи EntityFramework,
расположенные в в папке ../Infrastructure/Persistence/Migrations/.

Для выполнения миграций необходимо выполнять команды, находясь в ../Infrastructure/.

**Domain** Тут определены классы бизнес-сущностей и правила бизнес-логики.

**Presentation** Здесь объявлены контроллеры или minimal-api эндпоинты,
предоставляющие API для фронтенда, view-модели для представления данных и тому подобное.

Строка подключения находится в файле appsettings.json DefaultConnection.

В логику проекта была добавлена авторизация, теперь для работы с приложением необходимо авторизоваться,
чтобы получить токен для дальнейшей работы.

Для первичной регистрации пользователя необходимо обратиться к методу POST auth/register, передав туда

```json
{
  "login": "string",
  "password": "string",
  "role": 2
}
```

Для получения access токена обращаемся к методу: POST auth/login, передав

```json
{
  "login": "string",
  "password": "string"
}
```

В результате успешной авторизации будет получен токен, который в последующем необходимо передавать в
заголовках Authorization :  Bearer {token}.

При работе через Swagger есть возможность добавить токен, который автоматически будет добавлять в запросы.
Для этого в начале страницы необходимо нажать на кнопку Authorize => Login => и в открывшуюся форму вставить токен в формате Bearer {token}.

Ролевая модель так же дает возможность создать пользователя с ролью администратор (для этого передаем "role" : 1),
давая возможность удалять бронирования других пользователей, а так же работать с событиями.

 |---------------|--------------|-----------------------------------------------|

### BookingStatus
Статусы бронирования:
- `Pending` (1): Ожидает обработки.
- `Confirmed` (2): Подтверждено.
- `Rejected` (3): Отклонено.
- `Cancelled` (4): Отклонено пользователем.

Бронирование может принять статус `Rejected` (3), если в результате фоновой обработки бронирований возникли ошибки.
Пользователь так же может отменить свое бронирование, тогда статус будет `Cancelled` (4)

В логику метода добавлена примитивная логика с блокировкой, которая 
предотвращает ситуации овербукинга. Это может произойти когда на текущем событии закончиваются
места, а количетсво броней приходит в большом количестве. Секция с блокировкой запрещает
изменять переменную AvailableSeats для события разу из нескольких потоков.

### Проверка статуса бронирования
Метод GET `/bookings/{id}`
Возвращает текущее состояние бронирования.
Параметры:

**Параметры:**
 | Параметр | Тип   | Описание                     |
 |-----------|-------|------------------------------|
 | `id`      | Guid  | Идентификатор бронирования       |

 Взаимодействие между микросервисами реализовано через брокер Kafka.
 Инициализация необходимых топиков для консьюмеров реализована через отдельный контейнер kafka-init.

 После того, как на ранее созданное событие создается бронирование - в брокер BookingProducer посылает доменное событие bookings-created,
 которое содержит в себе BookingCreatedDomainEvent. Оно информирует микросервис EventsApplication о том, что было создано бронирование.

 После чего микросервис EventsApplication считывает топик bookings-created и обрабатывает его.
 В случае, если у события хватает мест и оно еще не началось EventProducer отправляет в Kafka доменное событие BookingProcessedDomainEvent
 в топик bookings-processed-success.
 Если условия бронирования не выполнились, то данное событие попадает в топик bookings-processed-unsuccess.

 Далее микросервис BookingsApplication считывает оба топика bookings-processed-unsuccess и bookings-processed-success
 и в зависимости от того в какой топик попало бронирование проставляет у него статус в базе даных. 

 Для отмены бронирования BookingProducer посылает в Kafka доменное событие BookingCancelledDomainEvent в топик booking-cancelled,
 после чего микроервис EventsApplication считает данное сообщение и освободит места у переданного события.

 ## Стратегия кеширования

### Что кешируется?
1. **Отдельные события** (`event:{id}`):
   - TTL: 5 минут (`EventCacheTTLSeconds`).
   - Инвалидация: при изменении события (обновление, удаление).
   - Причина: События могут часто изменяться (например, при бронировании), поэтому кеш обновляется явно.

2. **Топ-10 событий** (`events:top10`):
   - TTL: 10 минут (`TopEventsCacheTTLSeconds`).
   - Инвалидация: по TTL (явная инвалидация не используется).
   - Причина: Топ-10 — это агрегат, который меняется реже. Небольшое устаревание некритично.

### Устойчивость к ошибкам
- Если Redis недоступен:
  - Ошибки логируются, но **не пробрасываются** клиенту.
  - Запрос идёт **напрямую в базу данных** (кеш деградирует).
  - Это гарантирует, что приложение **продолжает работать** даже при падении Redis.

### Порядок операций при изменении данных
1. **Сначала обновляем базу данных** (чтобы данные были актуальными).
2. **Потом инвалидируем кеш** (чтобы следующий запрос обновил кеш).
   - Если инвалидация не удастся (например, Redis недоступен), **кеш обновится при следующем запросе** (через TTL или явную инвалидацию).
